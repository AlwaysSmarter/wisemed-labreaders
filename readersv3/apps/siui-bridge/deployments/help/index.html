# SIUI Bridge — API GENERAL și CLINICE

## Configurare și migrare

Setări → CNAS este exclusiv pentru utilitarul `siui-bridge`. Introdu codul fiscal (numai cifre), alege codul CAS din nomenclator și completează seria de licență. Utilizatorul CNAS se formează automat: `7991962_CAS-DJ`. Sunt incluse cele 45 de coduri InsuranceHouse din nomenclatorul furnizat `NomenclatoareClinice_20261001.xml`, inclusiv AOPSNAJ și MLPTL. Lista este un snapshot al acestui fișier, nu o interogare live CNAS.

Selectează CurrentUser/LocalMachine și certificatul/tokenul USB. Pentru fiecare pereche magazin + amprentă se păstrează adresa SIUI, portul (inclus în URL), adresa PE și excepția pentru valabilitatea certificatului serverului. La schimbarea certificatului, formularul încarcă profilul salvat; un certificat nou pornește cu adresele oficiale. Apasă Salvează înainte de executarea operațiilor.

Configurația este în `deployments/config.yaml`, secțiunea `modules.siui`. `username` vechi rămâne compatibil; câmpurile `fiscal_code` și `cas_code` au prioritate când sunt ambele completate. Configurația veche creează automat profilul certificatului activ. O licență goală la salvare păstrează valoarea existentă. GET întoarce numai starea și indiciul primele/ultimele 3 caractere. Nu se exportă cheia sau certificatul tokenului în CER.

```yaml
modules:
  siui:
    fiscal_code: "7991962"
    cas_code: CAS-DJ
    username: "7991962_CAS-DJ"
    licence: "LICENTA_CNАS"
    certificate_store: CurrentUser
    certificate_thumbprint: "AMPRENTA_SHA1_40_HEX"
    base_url: https://www.siui.ro
    pe_base_url: https://sipe.siui.ro
    allow_invalid_server_certificate_date: false
    database: ./siui-jobs.db
    certificate_profiles: [] # gestionat la salvarea din Setări
```

`base_url` trebuie să fie o origine HTTPS fără cale/query. Portul poate fi 443 sau 444, conform configurației CNAS. Originile personalizate se configurează local, nu pot fi injectate arbitrar prin API. Excepția TLS opțională ignoră doar perioada de valabilitate a certificatului serverului; numele, CA și utilizarea certificatului rămân verificate. Certificatul tokenului trebuie să fie valid. PE utilizează separat `https://sipe.siui.ro/svapntws/services/EPrescriptionWS`; OCSP utilizează originea SIUI și `/OCSP/validator`.

Setări → Server și actualizări păstrează serviciul, HTTP/HTTPS, logurile și actualizările. Secțiunile Comunicare analizor și Rezultate și WiseMED sunt ascunse numai pentru SIUI Bridge. Funcțiile comune de autentificare WiseMED și WSM rămân active.

## Autentificare HTTPS cu JWT

API-ul local al utilitarului folosește HTTPS și JWT HS256 pentru clienți direcți. Autentifică-te întâi prin mecanismul comun WiseMED (`POST /api/session/login`, aceleași date ca în interfața utilitarului). Cu cookie-ul de sesiune valid, cere `POST /api/siui/auth/token`, JSON `{}`. În Debug există butonul „Generează JWT pentru 15 minute”. WSM poate emite un JWT cu identitatea sa verificată.

Răspuns: `{"ok":true,"access_token":"...","token_type":"Bearer","expires_in":900}`. Utilizează `Authorization: Bearer <access_token>` la toate rutele `/api/siui/*`. Tokenul are `iss=siui-bridge`, `aud=siui-api`, `sub`, `iat`, `exp`, proprietarul semnat `owner` și rolul `admin` preluat din sesiune, nu din cerere. Cheia este aleatorie și ținută în memoria procesului: restartul invalidează JWT-urile emise. Sesiunea de browser SIUI folosește, de asemenea, o cheie aleatorie de proces; după actualizare/restart autentifică-te din nou. Un JWT nu poate emite alt JWT. Tokenurile nu sunt returnate în GET settings și nu sunt scrise în log.

Browserul folosește în continuare cookie-ul de sesiune. Un Bearer JWT direct este acceptat numai pe HTTPS, fără încredere implicită în X-Forwarded-Proto. Pentru reverse proxy, păstrează HTTPS până la utilitar. Importă CA locală pentru verificarea TLS; exemplele nu folosesc `curl -k`.

```sh
curl --cacert deployments/tls/wisemed-local-root-ca.pem \
  -H "Authorization: Bearer $SIUI_JWT" \
  https://localhost:19112/api/siui/catalog
```

Sesiunea OCSP CNAS este separată de JWT-ul API. Operațiile obțin automat o sesiune OCSP proaspătă folosind tokenul fizic, utilizatorul și licența CNAS. Antetul CNAS se numește intenționat `OSCP_RESPONSE`, iar SOAP folosește și `SessionID`.

## WSM

Pentru pagini WiseMED există wrapperul `SIUIBridge(objWSM, options)`, servit de WSM
la `/sdk/siui-bridge.js`. Acoperă toate cele 40 de operații CNAS și endpointurile
auxiliare, inclusiv polling, descărcări fragmentate și anularea așteptării locale.
[Integrare și inventarul metodelor](../../../../wsm-server/docs/siui-browser-wrapper.md).

SIUI Bridge trimite `client_type: "siui-bridge"` în mesajul `hello`. JWT-ul folosește rolul de autorizare `service`; cheia WSM trebuie să permită `service`. Identificatorii `reader_id` și `equipment_id` rămân pentru rutarea și legarea echipamentului. Pentru token_endpoint, emitentul trebuie să emită rolul solicitat `service`; token_file trebuie reemis cu acest rol. Actualizează și WSM pentru acceptarea acestui tip; rutarea după tip folosește `target: {"mode":"client_type","client_type":"siui-bridge"}` și necesită dreptul `route:broadcast`. Rutarea directă după echipament rămâne disponibilă.

Aceleași metode și corpuri JSON sunt accesibile prin comanda comună `api.request`, cu identitatea atestată de WSM. Nu se trimite JWT-ul local în acest mesaj. Exemplu de payload pentru adaptorul comun:

```json
{"method":"POST","path":"/api/siui/general/getInsured","body":{"operation_id":"insured-20261005-001","parameters":{"pid":"CNP_REAL","requestDate":"2026-10-05T00:00:00+03:00"}}}
```

Folosește anvelopa de comandă `api.request` descrisă în documentația comună `readersv3/docs/wss-control.md`. Răspunsul adaptorului conține `status`, `body` și tipul conținutului. Polling-ul folosește tot `api.request`, metoda GET și calea `/api/siui/calls/<id>`. Execuțiile sunt izolate pe proprietar; identitatea locală și identitatea WSM au spații separate. Un JWT emis prin WSM păstrează proprietarul și tenantul WSM, astfel încât poate urmări aceleași execuții. Nici un antet furnizat de client nu poate impersona identitatea WSM.

## Contractul comun al operațiilor

Fiecare operație SOAP: `POST /api/siui/<grup>/<operație>`, Content-Type `application/json`:

```json
{"operation_id":"id-unic-stabil","parameters":{"parametruWSDL":"valoare"}}
```

Toți parametrii sunt șiruri JSON, inclusiv `int`. Numele sunt case-sensitive și coincid cu WSDL; trimite exact câmpurile listate pentru operație. Parametrii WSDL `string` pot fi goi când convenția CNAS o permite; nu omite câmpul. `dateTime` trebuie să fie `YYYY-MM-DDTHH:mm:ss` cu fus orar opțional, de exemplu `2026-10-05T00:00:00+03:00`. XML se trimite ca șir JSON, nu ca SOAP; bridge-ul îl escapează automat.

Răspuns inițial: HTTP 202, `{"ok":true,"call":{"id":"...","operation_id":"...","operation":"getInsured","status":"queued"}}`. Citește `GET /api/siui/calls/<id>` până la o stare terminală:

- `queued`, `running`: în curs;
- `completed`: răspuns CNAS primit, în `call.result.values` (array de șiruri). NU înseamnă automat validare medicală sau administrativă reușită; interpretează XML-ul/starea CNAS;
- `failed`: eroare înainte de trimiterea unei modificări sau eșec de citire;
- `unknown`: o modificare ar fi putut ajunge la CNAS sau procesul s-a oprit înainte de finalizare. Reconciliază înainte de o nouă trimitere.

`operation_id` este obligatoriu (1–128 caractere, litere/cifre/`_.:-`, primul caracter alfanumeric). Repetarea aceluiași ID, operație, parametri și configurație întoarce execuția existentă (HTTP 200), fără retrimitere. Refolosirea cu alt conținut întoarce 409. Nu există retry automat al scrierilor. Coada serializează accesul la token; setările nu se schimbă cât există operații active. La restart, lucrările neterminate devin `unknown` și nu se reiau.

Operațiile care modifică datele și afișarea tokenului OCSP cer rol administrator. Citirile sunt disponibile utilizatorilor autentificați. Debug este interfața administratorului. HTTPS și WSM aplică aceleași reguli.

Timeout: 120 secunde per execuție SOAP, 25 secunde pentru testul OCSP. Limite: 1 MiB XML/parametru și răspuns SOAP; 2 MiB corp JSON; 64 MiB fișier descărcat. Nomenclatoarele și personalizările întoarse ca URL + dimensiune sunt descărcate automat de pe aceeași origine HTTPS SIUI; nu se urmăresc redirecturi și nu se trimit credențiale către alte gazde. Un URL extern se raportează ca eroare, fără a fi accesat.

Fișierele se păstrează în `siui-downloads` lângă baza SIUI, cu drepturi restrictive pe Unix. Metadatele apar în `call.result.file`. `GET /api/siui/calls/<id>/file?offset=0` întoarce `data_base64`, `next_offset`, `eof`, în fragmente de maximum 256 KiB. Repetă cu `next_offset` până la EOF. Funcționează identic prin WSM; butonul de descărcare din Debug reconstruiește fișierul. XML-urile/șirurile întoarse direct de PE sunt în `values`, fără transformarea lor în date fictive.

Baza SQLite păstrează identitatea, digestul cererii, starea și răspunsul CNAS. XML-ul cererii, licența și sesiunea OCSP nu sunt păstrate în istoric. Răspunsurile și fișierele pot conține date medicale; administratorul gestionează păstrarea și ștergerea lor. Nu există ștergere automată a istoricului în această versiune. Logurile conțin doar operația, ID-ul și starea.

## GENERAL — OCSP

`POST /api/siui/general/ocsp`, corp `{}`. Necesită administrator. Reutilizează sesiunea de maximum 150 secunde pentru aceeași configurație; altfel obține una nouă. În Debug butonul „Obține / reutilizează token OCSP” afișează tokenul, vechimea și rezultatul. Răspunsul reușit include `token`, `authenticated:true`. Tokenul nu se salvează în istoric, fișier, localStorage sau log; răspunsul are `Cache-Control: no-store`. Nu există refresh periodic documentat de CNAS; celelalte operații obțin singure sesiunea.

- `GET /api/siui/status`: platformă, configurare și număr de lucrări active.
- `GET /api/siui/settings`: administrator; configurare cu licență mascată și profiluri.
- `PUT /api/siui/settings`: administrator; `fiscal_code`, `cas_code`, `licence` (opțional), `certificate_store`, `certificate_thumbprint`, `base_url`, `pe_base_url`, `allow_invalid_server_certificate_date`. Transmite configurația completă a profilului selectat. Salvarea fără token este permisă pentru pregătire pe Mac; selectarea unui certificat nou este validată în magazinul de certificate al platformei.

- Vechile rute `/insured`, `/ocsp-test`, `/personalization`, `/validations` rămân pentru compatibilitate. `/validations` rămâne PARA; noul `/general/validateReport` suportă CLIN și PARA. `/ocsp-test` nu divulgă tokenul, `/general/ocsp` îl întoarce administratorului.

## Validare XML și interpretarea răspunsurilor

Toate câmpurile XML sunt verificate sintactic: fără DTD/directive, fără entități externe, adâncime maximum 40 și limită 1 MiB. Validările SIUI folosesc XSD-urile locale pentru raport CLIN/PARA, prescripții, trimiteri și concedii. PE processPrescribedPrescription, processHospitalPrescription și getPrescribedPrescriptionsForCid verifică XSD-urile cererilor lor. sendReport verifică XML-ul sintactic; schema raportului și regulile de business depind de categoria CNAS și sunt evaluate de server. Celelalte șiruri respectă tipurile WSDL. Bridge-ul păstrează răspunsul SOAP ca valori exacte, inclusiv codurile numerice și XML-urile, pentru interpretare de către aplicația apelantă.

## Diagnostic și testare

Pe Windows și macOS 12+ sunt disponibile și operațiile CNAS reale, cu driverul tokenului și acces la cheia privată. Pe Linux amd64/arm64, accesul la token pentru TLS și CMS necesită biblioteca PKCS#11 configurată local; configurarea, JWT, catalogul, OpenAPI și testul simulat rămân disponibile. Testul local nu verifică un CNP real și nu comunică cu CNAS. Rulează întâi OCSP, apoi getInsured sau getProviderInfo. Operațiile de trimitere/anulare au efecte reale; folosește date autorizate și un ID stabil.

401: autentificare invalidă/expirată; 403: rol insuficient; 400: parametri/date/XML incorecte; 409: configurație, token ocupat sau conflict ID; 503: worker/platformă indisponibilă. Erorile din execuție apar în `call.error`. Fault-urile SOAP sunt afișate în execuție, fără logarea XML-ului cererii. Un rezultat `unknown` nu se retrimite automat.

TLS 12175 include flags WinHTTP: `0x20` valabilitate certificat server, `0x8` CA necunoscută, `0x10` nume incorect, `0x80000000` negociere Schannel. PIN-ul cerut de driver nu dovedește autentificarea CNAS. Excepția pentru data certificatului este opt-in și se salvează pe profil.

## Token USB pe macOS

Instalează driverul producătorului cu suport CryptoTokenKit. În Setări → CNAS alege **Utilizator curent / macOS Keychain** (valoarea API `CurrentUser`), apasă **Reîncarcă certificatele**, selectează certificatul valid al tokenului și salvează profilul. `LocalMachine` este exclusiv Windows. Enumerarea include identitățile Keychain, inclusiv cele furnizate de token; un certificat fără cheie privată nu este suficient.

Bridge-ul accesează Security.framework direct, fără compilator, fără PKCS#11 configurat manual și fără fișiere CER sau export de cheie privată. Semnarea TLS se face prin driver; dialogul PIN/autorizare este afișat de macOS sau de driver. Pentru testare pornește utilitarul în sesiunea desktop a utilizatorului. Un serviciu de sistem fără sesiune grafică poate să nu poată afișa dialogul tokenului. Anularea cererii HTTP nu poate închide un dialog PIN deja deschis de driver.

În Debug → GENERAL testează întâi OCSP. Apoi poți executa `getInsured` sau `getProviderInfo` prin aceeași interfață, API HTTPS/JWT sau WSM. PIN-ul poate fi configurat criptat prin endpointul administrativ token-pin, separat de configurația YAML; vezi secțiunea PIN criptat. Pentru validare XSD pe macOS este necesar `xmllint`.

Transportul folosește TLS 1.2 și validarea nativă macOS a numelui și lanțului serverului. Opțiunea pentru certificatul CNAS expirat ignoră numai perioada de valabilitate; certificatele neîncredere și numele greșite rămân respinse. Intermediarii certificatului client sunt construiți în memorie din Keychain.

Depanare: `security list-smartcards` verifică driverul CryptoTokenKit; `security find-identity -v -p ssl-client` verifică identitățile accesibile contului. Aceste comenzi pot afișa datele titularului: nu publica ieșirea integrală. Detectarea certificatului nu confirmă autentificarea CNAS; aceasta necesită testul OCSP cu contul și licența configurate.

### Excepție explicită de revocare pe macOS

Setări → CNAS → **Permite certificatul serverului CNAS revocat (macOS)** corespunde câmpului API/YAML `allow_revoked_server_certificate`, implicit `false`. Se salvează în profilul certificatului selectat. Opțiunea acceptă riscul folosirii unui certificat revocat de autoritatea emitentă și este separată de excepția pentru expirare.

La eroarea nativă de revocare `-67820`, bridge-ul verifică din nou semnăturile lanțului, ancorele CA de sistem, numele DNS și utilizarea serverAuth, fără controlul de revocare. Expirarea rămâne verificată dacă opțiunea de valabilitate nu este activată. Un certificat necunoscut, un nume greșit sau o semnătură invalidă sunt respinse. Această opțiune nu schimbă transportul Windows.

### Codul imprimabil

Specificația PIAS 3.7.32, secțiunea 3.7.2, cere **DataMatrix**, nu QR. Anexa 008, secțiunea 2.4.2, precizează că datele sunt octeții XML-ului arhivat ZIP. Bridge-ul construiește `F`/`A` conform `InvoiceBarcode.xsd`, arhivează ca `invoice.xml` și codifică direct octeții ZIP în DataMatrix ECC200. Base64 este numai ambalajul JSON al răspunsului API, nu conținutul simbolului.

PNG-ul are margine albă și se poate descărca sau tipări împreună cu previzualizarea. Nu se trunchiază datele dacă depășesc capacitatea codului; `barcode_warning` explică situația, iar PNG-ul nu este generat. Previzualizarea este marcată ca document de test, netrimis; nu constituie confirmare CNAS sau șablon fiscal certificat.

### Semnare și trimitere efectivă

`POST /api/siui/invoice/package`, administrator, corp `{"invoice_xml":"<invoice ...>...</invoice>"}`: validează XSD, semnează octeții XML prin CMS SignedData atașat (SHA-256), arhivează CMS în ZIP și întoarce `invoiceFile` Base64. Nu transmite către CNAS. macOS folosește cheia CryptoTokenKit; Windows folosește signerul CSP/KSP când este disponibil un PIN furnizat, altfel SignedCms din System.Security prin PowerShell. Linux folosește PKCS#11. PIN-ul poate fi furnizat criptat conform secțiunii PIN criptat. Cheia privată nu este exportată. Windows necesită sesiune/driver capabil să afișeze dialogul PIN.

Butonul „Semnează cu tokenul și transmite” obține și afișează mai întâi un token OCSP în dashboardul de test, apoi semnează CMS și execută `sendEInvoice`, numai la acțiunea explicită a operatorului. ### Adresa conexiunii deasupra erorilor CNAS

Erorile de autentificare, SOAP și descărcare includ primele linii `Server: https://.../cale` și `Port: ...`, urmate de mesajul erorii. Se folosește conexiunea din etapa care a eșuat: un eșec OCSP nu este etichetat cu adresa eFactura. Interfața afișează mesajul pe linii separate deasupra rezultatului JSON, cu evidențierea roșie existentă. Erorile locale din operații, înainte de conectare, indică faptul că nu a fost inițiată conexiunea. Parametrii query ai adreselor de descărcare nu sunt adăugați la antetul de diagnostic, deoarece pot conține tokenuri.


### Loader și rezultat factură / limită OCSP — 13.10.2026

Butonul de semnare folosește loaderul standard (`is-loading`, `aria-busy`) pe întreaga durată OCSP → CMS → transmitere → rezultat. Progresul și mesajul final sunt afișate și lângă buton, nu doar înaintea previzualizării. Erorile și rezultatele incerte rămân roșii după reactivarea butonului; clickurile repetate în timpul aceleiași operații sunt ignorate.

Limita sa și cea a `ocsp-test` au fost aliniate de la 25 la 120 secunde, cu păstrarea anulării cererii clientului. Debugul indică limita, iar loggerul arată timpul disponibil și durata efectivă. Regresii DOM (jsdom opțional, instalat separat de aplicație): `NODE_PATH=/tmp/siui-ui-regression/node_modules node --test modules/localhttp/ui/siui-invoice-dom.test.cjs`. Scenarii: OCSP eșuat, CMS eșuat, polling eșuat, failed/unknown/completed, restaurarea butonului și ignorarea clickului duplicat. Toate folosesc API simulat, fără transmitere CNAS.


### Reutilizare OCSP pentru maximum 150 secunde

Sesiunea se păstrează exclusiv în memoria procesului, legată de configurația CNAS, inclusiv username (perechea CUI_CODCAS), licență, magazin/amprentă certificat și adrese/opțiuni TLS. Aceeași pereche CUI_CODCAS cu alt certificat sau altă configurație nu reutilizează sesiunea. La o vechime mai mare de 150 secunde se elimină tokenul și se obține unul nou. Un eșec de reautentificare nu readuce în uz tokenul expirat. Repornirea aplicației golește memoria.

Răspunsul OCSP include `reused`, `age_seconds`, `token_id` și `message`. Debugul arată tokenul complet și vechimea; loggerul arată un identificator SHA-256 scurt, nu valoarea secretă. Rezultatul operației SOAP include metadatele `ocsp` pentru sesiunea folosită efectiv. Intervalul de 150 secunde este politica cerută de operator, nu o durată de valabilitate garantată de CNAS. Limita de așteptare pentru obținerea unui token nou rămâne 120 secunde.


### Eșec de conectare înainte de transmiterea SOAP

O eroare Go tipizată net.OpError cu Op=dial, inclusiv încapsulată în url.Error, este clasificată `failed`: conexiunea nu a fost stabilită pentru acel apel. Erorile în timpul scrierii/citirii și timeouturile fără dovada etapei rămân `unknown` pentru operațiile care modifică date. Clasificarea nu se bazează pe căutarea textului erorii. Nu se reexecută automat apelul și nu se modifică stările apelurilor anterioare din istoric.


### Transport macOS: conexiuni TCP intermitente

Transportul macOS folosește un DialContext cu maximum trei încercări de stabilire TCP, câte maximum 10 secunde, cu pauză de 500 ms între ele. Se repetă exclusiv o eroare tipizată de timeout la dial, înainte de TLS și înainte de transmiterea octeților HTTP. Nu se repetă POST-ul după trimitere, nici erorile TLS, read/write sau refuzurile de conectare. Limita totală a operației și anularea rămân active.

Loggerul afișează server:port, numărul încercării, durata TCP și începutul/finalul negocierii TLS. Excepțiile configurate pentru certificatul serverului rămân aceleași; nu este introdusă o dezactivare globală a verificării TLS. Portul rămâne cel ales în Setări CNAS. Încercările TCP suplimentare atenuează conectivitatea intermitentă, fără să garanteze disponibilitatea serverului.


### Reîncărcarea automată a certificatelor

La pornirea SIUI Bridge și după autentificarea în interfață (inclusiv restaurarea unei sesiuni), se enumeră automat certificatele din magazinul configurat, folosind aceeași funcție nativă ca butonul „Reîncarcă certificate”. Deschiderea Setări → CNAS actualizează și lista vizibilă. Certificatul selectat și profilurile salvate se păstrează; nu se face autentificare OCSP în această etapă.

`POST /api/siui/certificates/refresh` necesită autentificare, nu necesită configurarea credențialelor CNAS și nu expune lista certificatelor. Enumerarea nu interferează cu o operație activă pe token: în acel caz se afișează eroarea și se poate reîncerca din Setări → CNAS. Loggerul înregistrează rezultatul enumerării la pornire/autentificare; erorile nu blochează pornirea sau loginul și sunt afișate în interfață după login.

SIUI poate returna pentru `getEInvoiceId` trei valori: `[număr înregistrare SIUI, BT-13, mesaj]`. A doua valoare este identificatorul BT-13 (corespondență confirmată de utilizator pe răspunsul SIUI), nu un mesaj de eroare; primele două valori se păstrează integral în `result.values` dacă mesajul final este gol. Exemplu: valoarea `1516712462512` de pe poziția 2 reprezintă BT-13. Mesajul „Factura are asociate raportări/deconturi dar nu a fost validată.” blochează folosirea ID-ului pentru e-Factura; bridge-ul îl tratează ca eroare și îl afișează prin fluxul existent de erori. Succesul transportului SOAP nu confirmă validarea CAS.


### PIN criptat și autentificare prin driver

În Setări → CNAS → PIN / parola tokenului se poate salva sau șterge PIN-ul certificatului activ. Interfața afișează numai `<hidden>` dacă există un PIN salvat. Câmpul de înlocuire este gol; salvarea setărilor generale nu modifică PIN-ul. Salvați mai întâi certificatul selectat. API-ul nu returnează nici PIN-ul, nici valoarea criptată.

`GET /api/siui/token-pin` (administrator) întoarce `configured`, `hint`, `blocked`, `failed_attempts`, `max_attempts` (3), `manual_required` și `pkcs11_module`. `PUT` acceptă `{ "pin": "..." }` pentru înlocuire, `{ "forget": true }` pentru ștergere, sau `{ "pin": "...", "manual": true }` pentru un PIN temporar, fără salvare pe disc. Nu introduceți valoarea literală `<hidden>` ca PIN. Câmpul gol din interfață nu trimite o modificare. Operațiile active pe token blochează schimbarea PIN-ului.

PIN-ul temporar este disponibil în memorie timp de maximum 150 secunde, astfel încât aceeași acțiune să poată realiza OCSP, semnarea CMS și conexiunea SOAP. La respingerea explicită a PIN-ului este eliminat. Folosirea lui suspendă PIN-ul salvat; succesul manual nu reactivează un PIN vechi care poate fi greșit.

Stocarea folosește `siui-token-pins.json`, în directorul bazei de date SIUI, cu înregistrări legate de magazinul certificatului, amprentă și biblioteca PKCS#11. Pe Windows se folosește DPAPI în contextul contului aplicației. Pe macOS/Linux se folosește AES-256-GCM cu o cheie de instalare separată (`siui-token-pins.json.key`), accesibilă numai contului aplicației (0600). PIN-ul nu este scris în YAML, baza de date a operațiilor, loguri sau argumentele proceselor. Un backup care conține atât depozitul Unix, cât și cheia acestuia permite decriptarea și trebuie protejat. Schimbarea contului Windows necesită reconfigurarea PIN-ului DPAPI.

Încercările automate sunt serializate în memorie. Contorul respingerilor se păstrează pe certificat inclusiv după restart. O semnătură reușită și verificată resetează contorul la zero; erorile fără legătură cu PIN-ul nu îl modifică. Se permite o nouă încercare la următorul apel, fără repetarea automată a operației CNAS. PIN-ul salvat este suspendat persistent la a treia respingere explicită de PIN/autentificare: CryptoTokenKit AuthenticationFailed pe macOS, SCARD_W_WRONG_CHV/SCARD_W_CHV_BLOCKED pe Windows, respectiv PIN incorrect/invalid/length-range/locked prin PKCS#11. Tokenul absent, anularea, erorile de comunicare cu driverul, de certificat, TLS sau rețea și repornirea procesului nu suspendă PIN-ul. Nu există retry automat al PIN-ului prin alt backend și nu se retransmite automat factura. Pentru reactivarea unei înregistrări deja suspendate se salvează din nou PIN-ul corect; suspendările existente nu sunt resetate automat la actualizare.

- macOS: `LAContext.setCredential` cu `smartCardPIN`, asociat identității CryptoTokenKit prin `kSecUseAuthenticationContext`. Încercarea automată interzice dialogurile interactive și elimină credentialul/invalidează contextul la încheiere. Fără PIN automat disponibil, operația următoare folosește fluxul clasic macOS. Suportul PIN-ului furnizat depinde de driver.
- Windows: cheia certificatului este accesată prin CSP (`PP_SIGNATURE_PIN` / `PP_KEYEXCHANGE_PIN`) sau KSP (`NCRYPT_PIN_PROPERTY`), în mod silent pentru încercarea automată. Handle-urile partajate sunt refuzate pentru a evita păstrarea credentialului într-un context extern. În modul PIN furnizat, TLS și CMS folosesc signerul nativ în același proces; TLS folosește transportul Go cu verificarea CA/nume și excepția de dată configurată. Fără PIN disponibil, rămân WinHTTP și PowerShell/SignedCms pentru introducerea clasică. KSP suportă RSA/ECDSA; CSP suportă RSA.
- Linux amd64/arm64: configurați **local** `modules.siui.pkcs11_module` cu calea absolută a bibliotecii producătorului sau OpenSC compatibile cu tokenul, apoi reporniți și reîncărcați certificatele. Calea nu poate fi modificată prin API-ul web, deoarece încărcarea unei biblioteci execută cod nativ. PKCS#11 este folosit atât pentru TLS client, cât și CMS (RSA PKCS#1 v1.5 / ECDSA, SHA-256/384/512). La `CKR_PIN_INCORRECT` nu se repetă loginul; un token blocat sau cu puține încercări rămase nu primește PIN salvat automat. Introducerea manuală se face prin PIN-ul temporar din setări; dispozitivele cu protected authentication path își gestionează interacțiunea. Cheile cu `CKA_ALWAYS_AUTHENTICATE` nu sunt încă suportate de această implementare. Pentru validarea XSD este necesar `xmllint`.

Nu sunt implementate hook-uri în ferestre și nici un eveniment universal de solicitare PIN. Evenimentele de prezență (`SCardGetStatusChange`, `TKTokenWatcher`) sunt un mecanism separat; acest patch păstrează reenumerarea la pornire/login și la cerere.

Verificări: teste pentru criptare, legarea de certificat, o singură încercare concurentă, suspendare după restart, expirarea PIN-ului temporar, răspunsuri API mascate și UI; test macOS al contextului LocalAuthentication fără accesarea unui token; compilare Windows; teste Linux cu SoftHSM izolat pentru semnare, TLS mutual, CMS, respingerea PIN-ului și recuperare manuală. Compatibilitatea cu fiecare middleware fizic Windows/macOS trebuie verificată separat. Nu s-a introdus un PIN pe tokenul fizic al utilizatorului și nu s-au transmis facturi către CNAS.

Referințe: [Microsoft PIN property](https://learn.microsoft.com/en-us/windows/win32/seccng/key-storage-property-identifiers), [Microsoft smart card architecture](https://learn.microsoft.com/en-us/windows/security/identity-protection/smart-cards/smart-card-architecture), [Apple smartCardPIN](https://developer.apple.com/documentation/localauthentication/lacredentialtype/smartcardpin), [OASIS PKCS#11](https://docs.oasis-open.org/pkcs11/pkcs11-base/v2.40/cos01/pkcs11-base-v2.40-cos01.html).


## Răspuns structurat pentru calitatea de asigurat

Operațiile `getInsured` și `getInsuredByCID` păstrează XML-ul original în
`call.result.values` și adaugă `call.result.insured`, identic prin HTTP/JWT și WSM:

```json
{
  "insured": {
    "pid": "1000000000000",
    "cid": "12345678901234567890",
    "state": "1",
    "categories": [{"code": "3", "validFrom": "2017-04-04"}],
    "states": [{"code": "SAL", "validFrom": "2017-04-04"}]
  }
}
```

PID/CNP, CID și codurile rămân șiruri; nu convertiți CID în număr JavaScript.
Toate intrările din categories și states sunt păstrate, inclusiv atributele
`validFrom`, `validTo` când există și orice alte atribute returnate de CNAS.
Listele absente devin `[]`. Atributele absente nu sunt inventate.
Codul `state` este transmis exact ca în XML (exemple: `1` asigurat,
`0` neasigurat, `3` decedat); codurile necunoscute sunt păstrate.
Aceste coduri nu sunt confundate cu lista `states` (de exemplu `SAL`).

Dacă valoarea returnată nu este un insuredResponse XML valid cu un singur
element insured, răspunsul păstrează `values` și adaugă `parse_error`, fără
`insured`. Verificați eroarea și răspunsul CNAS, nu interpretați lipsa datelor
ca neasigurat. Structurarea se aplică apelurilor noi; rezultatele deja salvate
nu sunt rescrise.

## Callback persistent către WiseMED: callwmapi

Toate cele 40 de operații asincrone din catalog (general, clinice, facturare)
acceptă opțional callwmapi, prin HTTP/JWT sau WSM api.request, inclusiv pentru
utilizatori obișnuiți autentificați. WiseMED verifică drepturile de scriere.
Restricțiile operației CNAS inițiale rămân aplicabile.
Endpointurile auxiliare/sincrone și cele vechi /insured, /personalization,
/jobs nu acceptă acest obiect; folosește operația corespunzătoare din catalog.

Exemplu pentru POST /api/siui/general/getInsured (CNP fictiv):

~~~json
{
  "operation_id": "insured-patient-20261018-001",
  "parameters": {
    "pid": "1000000000000",
    "requestDate": "2026-10-18T10:00:00+03:00"
  },
  "callwmapi": {
    "lt": "TOKEN_LOGIN_WISEMED_OPTIONAL",
    "apipath": "/pacient/{cnp_pacient}",
    "method": "POST",
    "transform_path": [
      {"from_field": "cnp", "to_field": "cnp_pacient"}
    ],
    "body": {
      "verificare_la_data": "2026-10-18 10:00:00",
      "transform_result": [
        {"from_field": "cid", "to_field": "cid_pacient"},
        {"from_field": "state", "to_field": "stare_asigurare_cas"}
      ]
    }
  }
}
~~~

După un rezultat CNAS valid, bridge-ul trimite POST /pacient/1000000000000
la baza API WiseMED configurată (de exemplu /api), cu Authorization: Bearer
JWT generat cu cheia existentă și Idempotency-Key: siui-<call.id>.

~~~json
{
  "verificare_la_data": "2026-10-18 10:00:00",
  "cid_pacient": "12345678901234567890",
  "stare_asigurare_cas": 1
}
~~~

Nu se transmite cheia în callwmapi, în coadă sau în răspuns. Livrarea nu depinde
de cookie-ul sau de menținerea deschisă a clientului inițiator. Sunt acceptate
POST și PUT. URL-urile externe, query-stringurile, traversarea directoarelor
și redirecționările HTTP sunt refuzate.

Tokenul opțional callwmapi.lt este transmis exclusiv în claim-ul lt din JWT-ul
Authorization către WiseMED, fără login prealabil. În absența lui, apelul este
trimis fără lt; sesiunea globală a ultimului utilizator logat nu este folosită.
Bridge-ul nu poate determina anticipat dacă endpointul acceptă lt; WiseMED
decide și poate refuza cererea. HTTP 401/403 marchează livrarea failed, fără
reîncercare automată sau eliminarea tokenului. Tokenul nu apare în status sau
loguri. Specificațiile care conțin lt sunt criptate la salvare: DPAPI pe Windows,
respectiv cheia locală <database>.wm-callback.key pe macOS/Linux. Păstrează cheia
la restaurarea bazei de date; pe Windows este necesar același context DPAPI.

### Transformări

- transform_path citește parametrii inițiali. cnp este alias pentru pid.
  Sunt acceptate și pid sau parameters.pid. to_field identifică placeholderul
  din cale, nu numele parametrului original.
- body păstrează câmpurile fixe ca valori JSON; transform_result este o
  instrucțiune și nu se trimite la WiseMED. Data furnizată de client nu este
  recalculată la momentul livrării.
- transform_result.from_field acceptă căi precum result.insured.cid,
  insured.cid, cid, insured.categories, values.0 sau insured.categories.0.code.
  Aliasurile cid, pid, state, categories și states provin din result.insured.
- to_field este cheia de nivel superior din body; transformarea înlocuiește
  un eventual câmp fix cu aceeași cheie.
- Tipul JSON se păstrează. Starea asiguratului (state, insured.state sau
  result.insured.state) este implicit convertită în integer. CID/CNP rămân
  șiruri pentru a evita pierderea preciziei.
- Mapările rezultatului pot specifica type: string, integer, number sau boolean.
  type nu este utilizat la maparea căii.
- Câmpurile sursă lipsă, conversiile invalide sau result.parse_error opresc
  livrarea cu failed; nu se trimite un body incomplet.
- Pentru celelalte servicii CNAS, completed indică primirea răspunsului,
  nu interpretarea automată a tuturor erorilor de business din values.

### Coada și recuperarea

Configurația callback-ului este salvată împreună cu rezervarea apelului.
Rezultatul CNAS și body-ul pregătit sunt salvate într-o tranzacție înainte
de trimitere. Închiderea clientului sau repornirea bridge-ului nu pierde
livrările în așteptare.

GET /api/siui/calls/{id} întoarce separat starea CNAS și starea livrării:

~~~json
{
  "call": {
    "status": "completed",
    "callwmapi": {
      "status": "delivered",
      "attempts": 1,
      "http_status": 204
    }
  }
}
~~~

Stările callback-ului sunt waiting (așteaptă CNAS), pending (așteaptă livrarea),
sending, delivered (HTTP 2xx), failed (transformare, respingere sau încercări
epuizate), skipped (CNAS a eșuat sau rezultatul este necunoscut).
Eroarea livrării este disponibilă în call.callwmapi.error.

Maximum 5 încercări automate, timeout 30 secunde, pauze 30/60/120/240 secunde
pentru erori de transport, HTTP 429 și 5xx. Celelalte răspunsuri non-2xx sunt
definitive. Un HTTP 2xx este considerat livrat; răspunsul de business WiseMED
nu este interpretat. Coada folosește workerul bridge-ului, astfel că operațiile
CNAS în curs pot întârzia livrarea. Schimbarea bazei API împiedică trimiterea
callback-urilor vechi către noua instanță WiseMED.

**Livrarea este at-least-once, nu exactly-once.** Dacă WiseMED aplică modificarea,
dar confirmarea se pierde, bridge-ul poate retransmite aceeași cerere.
**Endpointul WiseMED trebuie să deduplice atomic după Idempotency-Key** și să
returneze rezultatul primei cereri pentru aceeași cheie. Implementarea de aici
nu modifică proiectul PHP. Body-ul și cheia sunt stabile la reîncercare.

Același operation_id cu aceeași cerere nu repetă operația CNAS sau callback-ul.
Schimbarea callwmapi pentru același ID produce HTTP 409.

Proprietarul autentificat al apelului poate relua exclusiv livrarea eșuată, cu body deja pregătit:
POST /api/siui/calls/{id}/callwmapi/retry. Aceasta resetează bugetul încercărilor,
păstrează cheia de idempotency și nu reapelază CNAS. Se aplică izolarea pe
proprietarul apelului.

Dacă bridge-ul se oprește înainte de salvarea rezultatului CNAS, apelul devine
unknown și callback-ul skipped; CNAS nu este reapelat automat. Mecanismul nu
poate recupera un răspuns CNAS care nu a fost încă salvat.

## Procesarea fișierelor descărcate prin HTTP și WSM

GET /api/siui/calls/{id}/file acceptă, pe lângă offset, unzip=true|false,
entry (nume exact din ZIP), format=bytes|xml|json și validateXSD=false (dezactivează XSD).
Răspunsul rămâne JSON cu data_base64, offset, next_offset, eof. Offseturile se
referă la rezultatul procesat; păstrează aceleași opțiuni la toate fragmentele.
Ordine: extragere ZIP → validare XSD implicit activă → conversie → fragmentare.
Parametrii absenți păstrează descărcarea originală. ZIP cu mai multe fișiere
necesită entry. Erorile de procesare întorc HTTP 422, fără modificarea rezultatului
CNAS salvat. Limita intrării/fișierului extras/ieșirii este 64 MiB. Procesarea este
recalculată la fiecare fragment; pentru fișiere mari este preferabil bytes fără
procesare. Nicio intrare ZIP nu este scrisă pe disc.
XML/JSON interzic DTD și adâncimi peste 40. JSON păstrează arborele:
name, namespace, attributes:[{name,namespace,value}], content:[text|nod,...].
Identificatorii rămân șiruri. Serverul alege schema și folosește validatorul existent și limita XSD
de 1 MiB; schema necunoscută sau validatorul indisponibil produce eroare, nu succes.
Un PDF nu poate fi convertit în XML/JSON prin acest endpoint.

Wrapperul WSM siui-bridge.js descarcă automat fișierele pentru operațiile așteptate
și poate solicita procesarea prin options.file. Trimite callback-ul WiseMED prin
options.callwmapi, inclusiv lt. Documentația și exemplele complete:
[SIUI browser wrapper](../../../../wsm-server/docs/siui-browser-wrapper.md).

### callwmapi.file: personalizare XML → JSON înainte de update WiseMED

callwmapi poate include file:{unzip:true,entry:"numele-real.xml"}.
Toate câmpurile sunt opționale; omiterea entry este permisă doar dacă ZIP-ul are
un singur fișier. Validarea XSD este implicit activă; validateXSD:false o dezactivează. Prezența file cere
procesare pe server și conversie XML → JSON; rezultatul este disponibil în
transform_result prin from_field:"file_json". De exemplu:
~~~json
{
  "callwmapi":{
    "apipath":"/cnas/personalisation",
    "method":"POST",
    "file":{"unzip":true},
    "body":{"transform_result":[{"from_field":"file_json","to_field":"personalisation"}]}
  }
}
~~~
lt poate fi adăugat opțional. Body-ul final (cu JSON) se salvează în aceeași
tranzacție cu rezultatul CNAS și se reutilizează la retrimitere. Fișierul original
nu este modificat. Eroarea de procesare marchează callback-ul failed; operația
CNAS completed rămâne distinctă. Conversia nu depinde de browser.
Nu există retry pentru transformare eșuată prin ruta de retry a livrării
(aceasta cere body deja pregătit).
Exemplele complete pentru asigurat, personalizare și validare 72h sunt în

### Alegerea XSD pe server și compatibilitatea cu actualizările CNAS

Clientul nu transmite numele XSD. Procesarea XML validează implicit cu schema
selectată de bridge din operația salvată și parametrii ei (ex. partnerCategory).
Pentru personalizare sunt incluse definițiile MF, CLIN, PARA, STOM, AMB, MD, HC,
SPT, NHP, DIA, SICK, CBRET. PHM și REC au variante diferite: fără o identificare
neambiguă serverul refuză validarea, nu ghicește. Fișierele vechi fără contextul
schemei produc aceeași eroare. Descărcarea originalului ZIP/PDF fără procesare
rămâne neschimbată.

Dacă CNAS actualizează XML/XSD înaintea bridge-ului, se poate cere explicit:
~~~js
file: {unzip:true, format:'json', validateXSD:false}
~~~
Pentru callback: callwmapi.file:{unzip:true,validateXSD:false}.
False dezactivează doar verificarea XSD; XML-ul malformat, DTD și limitele de
procesare rămân verificate. Nu există fallback automat după o eroare XSD.
Această opțiune privește procesarea fișierelor de răspuns, nu dezactivează
validările existente ale XML-ului de raportare trimis către CNAS.

## Operations — jurnal local și acces History

Meniul principal **Operations** (`/operations`), la același nivel cu Settings,
afișează apelurile din `siui_calls` și validările din `siui_jobs`. Include și
operațiile pasive înregistrate de Bridge. Implicit selectează ziua curentă în
fusul browserului, cu intervalul complet; se pot filtra orele, operația, starea
și `operation_id`. Lista se reîncarcă la 3 secunde, cu pagini de 100 de apeluri.
Administratorul vede toate apelurile; ceilalți utilizatori văd numai apelurile
identității autentificate. Un utilizator HTTP și un subiect WSM nu sunt uniți
automat doar pentru că au aceeași denumire.

Endpointuri disponibile prin HTTP(S) autentificat și WSM `api.request`:

- `GET /api/siui/operations?from=<RFC3339>&to=<RFC3339>&operation_id=...&operation=...&status=...&offset=0`
  — `calls`, `total`, `offset`, `next_offset`; `to` este exclusiv. Fără from/to,
  API-ul folosește întreaga zi curentă în fusul serverului.
- `GET /api/siui/operations/{id}` — cerere (`parameters`), rezultat/eroare,
  apelant, IP, conexiune WSM, timpi, evoluția stărilor și starea sincronizării History.
- `GET /api/siui/operations/{id}/file?offset=0` — fișierul local, în fragmente,
  cu aceleași reguli de acces ca detaliile apelului.
- `GET /api/siui/operations/{id}/history` — înregistrarea din History, prin proxy
  autentificat server–server. Cheia History nu ajunge în browser.
- `GET /api/siui/operations/{id}/history/{artifact}` — descărcare din History,
  transmisă în flux; cu `?offset=0` întoarce JSON `data_base64`, `next_offset`,
  `size`, în fragmente de maximum 256 KiB, inclusiv prin WSM.

Stările reale sunt `queued`, `running`, `completed`, `failed`, `unknown`.
`completed` înseamnă încheierea execuției; rezultatul poate conține erori de
business CNAS. Evenimentele noi sunt salvate tranzacțional în
`siui_operation_events`. Pentru apelurile anterioare actualizării se păstrează
starea existentă cu `snapshot=true`, fără a inventa timestampul tranziției.
Metadatele apelantului sunt în `siui_operation_sources`. Cererea, rezultatul,
sursa și evenimentele sunt incluse și în `record-gzip` pentru arhivările noi.
Nu este o captură de trafic TLS/SOAP; sunt datele cererii și rezultatului păstrate
de Bridge. Fișierele descărcate rămân fișiere, fără conversie implicită în JSON.

IP-ul HTTP este peer-ul conexiunii (poate fi un proxy). IP-ul WSM este adăugat
de WSM Server în `sender_ip`, suprascriind orice valoare furnizată de client.
Necesită actualizarea serverului WSM pentru această metadată. Cu un server vechi
sau pentru apeluri vechi, IP-ul poate fi indisponibil; conexiunea și proprietarul
sunt afișate când există. Nu se deduce IP-ul utilizatorului din antete neverificate.
Linkurile History funcționează numai pentru destinația/identitatea la care s-a
trimis apelul. Indisponibilitatea History nu blochează lista sau detaliile locale.


## Dashboard operațional și filtre Operations

Pagina principală SIUI Bridge prezintă apelurile completed/failed/unknown, rata de finalizare,
graficele de activitate și distribuție, volumul pe operație, încărcarea cozilor, OCSP, WSM,
livrările History/callwmapi, operațiile active și ultimele erori. Actualizare la 5 secunde.
Completed înseamnă finalizare tehnică, nu acceptare medicală/decontare.

Dashboard și Operations oferă Azi, Ieri, Săptămâna curentă (de luni), Ultimele 7 zile,
Luna curentă și Personalizat. Săptămâna/luna se termină la sfârșitul zilei curente.
Operations permite zile și ore diferite de început/final, Operation ID, operație și stare.
Ora finală goală include întreaga zi finală; altfel ora finală este exclusivă.
Datele sunt interpretate în fusul browserului, apoi transmise API în RFC3339.
Implicit este selectată întreaga zi curentă. Lista se actualizează la 3 secunde.
Taguri: completed/archived verde, running albastru, queued/pending/unknown galben,
failed roșu. Detalii păstrează tranzițiile, cererea/răspunsul și accesul History/fișiere.

### API dashboard

- `GET /api/siui/dashboard?from=<RFC3339>&to=<RFC3339>`: maxim 31 zile calendaristice;
  implicit ziua serverului. Returnează counts, hourly, by_operation, queue,
  recent_failures, deliveries, runtime, ocsp, endpoints și endpoint_evidence.
- `POST /api/siui/dashboard/checks`: administrator; sonde HEAD pe adresele configurate,
  timeout 6 secunde/URL, maximum 4 simultan, cache 60 secunde. Dashboardul le cere
  automat cel mult o dată pe minut. Nu folosesc tokenul sau PIN-ul.
- Rutele sunt disponibile și prin transportul WSM API existent, cu aceleași drepturi.

Statisticile apelurilor și livrările respectă proprietarul: administratorul vede întregul
bridge; utilizatorul obișnuit vede apelurile proprii. Încărcarea runtime este globală.
Coada activă (primele 100), livrările și ultimele erori sunt independente de interval.
Dashboardul citește metadatele locale fără să descarce arhive/parseze XML-uri mari.

Sondele verifică strict TLS, fără excepțiile transportului nativ și fără certificat client.
HTTP 401/403/405 arată doar că serverul răspunde, nu confirmă funcționarea SOAP.
Erorile TLS ale sondelor pot coexista cu apeluri native reușite. Fiecare serviciu afișează
separat ultima operație completed și ultima failed/unknown: observații istorice, nu teste
live ale adresei configurate acum.

OCSP afișează sesiunea procesului curent, ultima încercare/reușită și timpul rămas pentru
reutilizare, fără a expune tokenul. Expirarea cache-ului nu indică indisponibilitate.
Testul OCSP este manual, pentru administrator, și poate declanșa dialogul PIN.

Numele fișierelor descărcate folosește parametrul `fileName` din URL-ul CNAS,
cu extensia `.zip` sau `.xml` detectată din conținutul original. Exemplu:
`/svapntws/download?fileName=7pf6aug8hu06t1k5ff9gnc` produce
`7pf6aug8hu06t1k5ff9gnc.zip` pentru ZIP sau `.xml` pentru XML.
Metadatele `result.file.filename` și `content_type` sunt păstrate și în arhiva History.


## Cererea SIUI și fișierele trimise

Operations (Bridge) și Istoric (History) oferă parametrii cererii, separat de rezultat/eroare.
Parametrii aplicației sunt păstrați integral în `record.json.gz`; pentru apelurile noi,
copia din SQLite nu mai este golită după arhivare. Nu se adaugă PIN-ul, cheia privată
sau tokenurile de autentificare în această secțiune.

Câmpurile XML (`xml`, `reportXML`, `reportXml`, `requestXml`) se arhivează și separat,
cu nume `request-<parametru>`, păstrând exact octeții textului primit. `invoiceFile`
Base64 se decodează în `invoiceFile.zip` fără modificarea arhivei semnate.
Fișierele au dimensiune și SHA-256 în manifest și folosesc transferul reluabil existent.
Un fișier asociat unui apel queued/failed dovedește conținutul cererii, nu că SIUI l-a primit;
verifică starea și răspunsul operației.

- Bridge: `GET /api/siui/operations/{id}/request?name=request-reportXML`
  descarcă fișierul local; `offset` cere fragmente JSON Base64 pentru WSM.
  Metadatele de download sunt în `call.request_files`.
- History: `GET /api/history/calls/{id}/request?bridge=<bridge>` afișează parametrii
  din arhiva confirmată. Parametrul bridge este necesar pentru administrator.
- Prin Bridge: `GET /api/siui/operations/{id}/history/request` citește aceeași cerere
  fără expunerea credențialelor History. Fișierele folosesc rutele de download existente.

Previzualizarea limitează fiecare valoare la 4096 octeți; datele originale rămân intacte.
History limitează citirea pentru previzualizare la 64 MiB decomprimați; peste această
limită se descarcă arhiva integrală. Pentru arhivele mai vechi cererea rămâne în
`record.json.gz`; fișierele separate nu sunt generate retroactiv. Dacă vechiul Bridge
a golit copia locală, folosește „Vezi cererea arhivată” din detaliile History.


## Administrare spațiu local

Dashboard → Spațiu local · descărcări SIUI (administrator) arată dimensiunea în MB/GB,
numărul de fișiere și procentul eliberabil față de totalul descărcărilor locale, nu față
de capacitatea discului. „Actualizează spațiul” rescanează directorul fără a citi conținutul
arhivelor. „Șterge copiile locale arhivate” cere confirmare și verifică SHA-256 înainte
să elimine fiecare fișier. Sunt păstrate fișierele fără confirmare History, cele cu hash
necorespunzător și cele asociate callbackurilor care nu sunt delivered (inclusiv failed,
pentru a permite reîncercarea). Cererile, metadatele și istoricul nu sunt șterse.

Fișierele noi sunt în `<director SQLite>/siui-downloads/AN/LUNA/AAAA-LL-ZZ/<call_id>`,
folosind data UTC a descărcării. La verificarea spațiului, fișierele vechi din rădăcină
sunt mutate folosind data UTC a apelului (data fișierului dacă apelul nu mai există).
Citirea acceptă ambele structuri în timpul migrării. Nu se suprascriu fișiere existente.
Fișierele deschise/transferurile sunt protejate prin lock; dacă sunt ocupate, administrarea
răspunde 409 și poate fi reîncercată. Curățarea este manuală, fără retenție automată.

API HTTP/WSM, administrator:
- `GET /api/siui/downloads/storage`: statistici și migrare a structurii vechi.
- `POST /api/siui/downloads/storage` cu `{"confirm":true}`: curățare; întoarce
  `removed_files`, `removed_bytes` și `errors` în obiectul `storage`.

După curățare, descărcarea originalului prin API Bridge este preluată din History,
folosind destinația autorizată a apelului. History trebuie să fie disponibil. Procesarea
locală ulterioară (unzip/XSD/JSON) pe un fișier eliminat întoarce o eroare explicită;
nu întoarce în locul rezultatului procesat arhiva brută. Originalul rămâne descărcabil din History.


## Prescripții: carnete, prescriere și eliberare

Catalogul include toate cele 13 operații din `EPrescriptionWS`, cele două operații de carnete din `SiuiWS` și `getPrescription` / `validatePrescription` din `SiuiValidateWS`. Metodele adăugate:

| Metodă singleton | Parametri WSDL, în ordine | Modifică CNAS |
| --- | --- | --- |
| `general.generatePrescriptionSeries` | `categoryCode` (string), `orgUnitCode` (string), `uic` (string), `subUnitCode` (string), `validFrom` (dateTime), `isOnLine` (boolean), `quantity` (int) | Da |
| `general.getPrescriptionSeriesInfo` | `categoryCode` (string), `orgUnitCode` (string), `uic` (string), `subUnitCode` (string) | Nu |
| `clinice.processIssuedPrescription` | `reportXml` (string) | Da |
| `clinice.cancelReleasedPrescription` | `providerCode` (string), `workplaceCode` (string), `insuranceHouseCode` (string), `series` (string), `no` (string), `fractionNo` (int), `cancellationReason` (string) | Da |
| `clinice.updateInvoices` | `requestXml` (string) | Da |
| `clinice.getReleasedPrescription` | `providerCode` (string), `workplaceCode` (string), `insuranceHouseCode` (string), `series` (string), `no` (string), `fractionNo` (int) | Nu |

Toți parametrii se trimit ca șiruri JSON, cu excepția parametrilor declarați nullable. Pentru cele două operații de carnete, `subUnitCode` acceptă și JSON `null`, transmis SOAP ca `xsi:nil="true"`. Acesta este cazul unității cu personalitate juridică și contract direct cu CAS. Pentru o subunitate, se transmite `partnerCode` din personalizare. Nu folosi textul `"null"`. Un câmp nullable gol în Debug este trimis ca null; API-ul distinge între null și șirul gol. `isOnLine` acceptă exact `"true"`, `"false"`, `"1"`, `"0"`; `quantity` și `fractionNo` sunt șiruri de întregi pe 32 de biți. Carnetele sunt în GENERAL deoarece acesta este serviciul lor CNAS. Nu există parametru `stencilNo` la aceste două operații: `categoryCode`, `orgUnitCode`, `uic` și `subUnitCode` trebuie completate conform identității contractuale CNAS, fără a presupune că `subUnitCode` este parafa medicului.

`getPrescriptionSeriesInfo` interoghează carnetele existente la CNAS pentru parametrii furnizați, inclusiv cele generate prin altă aplicație dacă sunt accesibile aceleiași identități. WSDL-ul nu garantează că aceasta este lista tuturor carnetelor unui medic, indiferent de furnizor/contract. `generatePrescriptionSeries` generează carnete cu `validFrom`, `isOnLine` și `quantity`. Conform specificației PIAS §5.20, cele două valori din `result.data.result.values` sunt URL-ul fișierului de răspuns și dimensiunea lui. Backend-ul descarcă fișierul de pe aceeași origine HTTPS CNAS; singletonul returnează implicit conținutul ca `result.data.download.data` / `bytes` (Uint8Array), cu metadate în `result.data.result.file`. `download:false` oprește transferul browserului, fără a anula descărcarea backend-ului. Conținutul fișierului trebuie interpretat pentru a extrage carnetele; valorile SOAP nu sunt lista de carnete.

- Prescriere/validare PE: `clinice.processPrescribedPrescription({reportXml}, options)`, cu verificare locală `PhysicianDrugPERequest.xsd` înainte de trimitere.
- Preluare/anulare prescriere: `clinice.getPrescribedPrescription` / `clinice.cancelPrescribedPrescription`.
- Eliberare la farmacie: `clinice.processIssuedPrescription`, `clinice.getReleasedPrescription`, `clinice.cancelReleasedPrescription`. „Issued/released” desemnează eliberarea, nu prescrierea de către medic.
- Spitalizare: `clinice.processHospitalPrescription`, `clinice.getReleasedHospitalPrescription`, `clinice.cancelReleasedHospitalPrescription`.
- Consultare/rapoarte: `clinice.getStatusForPrescriptions`, `clinice.getPrescribedPrescriptionsForCid`, `clinice.downloadNotReportedPrescriptionsReport`; `clinice.updateInvoices` actualizează facturile în serviciul PE.
- Prescripții SIUI clasice: `clinice.getPrescription` și `clinice.validatePrescription` (distincte de PE).

### Online și offline

`isOnLine:"false"` generează un carnet pentru fluxul offline; apelul de generare în sine necesită conexiune CNAS. În schema PE inclusă, atributul rețetei `reportedOnline="0"` înseamnă prescriere offline de medic și validare online de farmacie; `reportedOnline="1"` înseamnă prescriere și validare online de medic. Schema cererii permite și `senderType="M"` / `"F"`, precum și `isCancelled` pe rețetă. Aceste câmpuri nu înlocuiesc operațiile SOAP de anulare și nu garantează acceptarea de CNAS a oricărei combinații.

Emiterea fără conexiune, alegerea și consumul unui număr din carnet, stocarea rețetei, tipărirea și sincronizarea ulterioară sunt responsabilitatea aplicației WiseMED. Bridge-ul nu implementează registrul local de carnete și nu rezervă automat numere pentru mai multe stații. Nu există validare de business CNAS fără conexiune și nici retrimitere automată a rețetelor la reconectare.

`processIssuedPrescription` și `updateInvoices` verifică XML-ul sintactic; în resursele incluse nu există XSD-uri de cerere pentru aceste două operații. Nu se aplică schema medicului la eliberarea farmaciei. Regulile de business se evaluează de CNAS. `success:true` / `completed` confirmă primirea răspunsului, nu acceptarea rețetei/carnetului; verifică valorile/XML-ul CNAS.

Folosește un `operationId` stabil pentru fiecare intenție de modificare. După timeout sau `unknown`, urmărește apelul existent și reconciliază prin operațiile de preluare înainte de a iniția altă modificare. Nu genera un ID nou doar pentru a repeta generarea carnetului.

Exemplele cu spinner, callback și `$.aceOverWatch` sunt în `examples/browser/siui-prescriptions.js` din pachetul WSM (în repository: `wsm-server/examples/browser/siui-prescriptions.js`).

```js
const parameters = {categoryCode: "...", orgUnitCode: "...", uic: "...", subUnitCode: null};
await SIUIPrescriptions.getPrescriptionSeriesSIUI(target, parameters,
    function(responseReceived, values, errorMsg, call) {
        if (!responseReceived) return;
        console.log(values); // interpretează răspunsul real CNAS
    });

// Creează și păstrează împreună acest ID și acești parametri pentru aceeași intenție.
const generationId = crypto.randomUUID();
const generationParameters = {...parameters,
    validFrom: moment().format("YYYY-MM-DDTHH:mm:ssZ"),
    isOnLine: "false", quantity: "1"
};
await SIUIPrescriptions.generatePrescriptionSeriesSIUI(target, generationParameters,
    generationId, function(responseReceived, values, errorMsg, call) {
        if (!responseReceived) return;
        console.log(values); // verifică acceptarea CNAS înainte de mesajul de succes
    });
```
